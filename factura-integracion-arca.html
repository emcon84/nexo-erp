Sistema de Facturación Electrónica ARCA

pullstok-erp · Backend (Express + Prisma) + Frontend (React/Vite) · Mapa del flujo completo

La clave: la facturación tiene DOS números distintos que conviene no confundir. El interno (FAC-XXXX) es de trazabilidad del sistema y no tiene valor fiscal. El fiscal (0002-00000008) es el real, otorgado por ARCA.

1. Los dos números

NúmeroQué esQuién lo genera
FAC-0001Referencia interna del sistema (trazabilidad, antes de ser fiscal)Contador por organización (Counter)
0002-00000008Número fiscal real (punto de venta 4 díg + comprobante 8 díg)ARCA / ArcaSequence

La factura nace como FAC-XXXX (sin valor fiscal). Recién cuando se emite contra ARCA se le asigna el número fiscal + CAE.

3. El orquestador de emisión — api/src/services/fiscalInvoiceService.ts

Dirige la emisión fiscal.

  • emitirFiscalmente(invoiceId, client, ctx) — emite una factura ISSUED interna aún sin CAE.
  • reintentarFiscalmente(invoiceId, client, ctx) — reintenta desde PENDING_CAE reutilizando el mismo cbteNro.
  • emitirCore(...) — el corazón:
    1. Decide Factura A vs B (deriveReceptorFiscal): CUIT válido → A, DNI/sin CUIT → B, CUIT inválido → bloqueado.
    2. Reserva el correlativo (cbteNro).
    3. Marca PENDING_CAE + guarda campos fiscales (transacción corta).
    4. Pide el CAE a ARCA (fuera de la transacción).
    5. Si ARCA dice "ya registrado" → consulta para recuperar el CAE.
    6. Si falla → queda PENDING_CAE con código de error y contador.
    7. Si va bien → ISSUED con CAE + vencimiento.

Estados de la factura

DRAFT ──issue()──▶ ISSUED (interna, sin CAE) ──emitirFiscalmente──▶ PENDING_CAE (reservando número) ──FECAESolicitar──▶ ISSUED (con CAE) fallo ──▶ PENDING_CAE (reintento, mismo cbteNro)

4. El cálculo fiscal — api/src/services/arcaCalc.ts

  • Decide A vs B (normalizeCuit, isValidCuit, deriveReceptorFiscal).
  • Mapea la alícuota interna al ID de ARCA (mapAlicuotaId: 21→5, 10.5→4, etc.).
  • calcArcaAmounts calcula montos en centavos enteros (evita errores de redondeo).

6. Multi-tenant (organización)

  • El cliente extendido de Prisma inyecta automáticamente organizationId en todos los modelos de tenant (Invoice, Product, Customer...).
  • ArcaSetting, ArcaSequence y Counter están fuera del scope automático: se acceden explícitamente por organizationId vía basePrisma (evita fugas entre organizaciones).
  • Los certificados nunca van en la BD: solo certPath/keyPath en el VPS (/var/www/pullstok/certs/{org}/...crt/.key).

8. Flujo completo de emisión

1. Front: useConfirm → issueInvoice(id) → PUT /api/invoices/:id/issue 2. Backend: marca ISSUED interna con número FAC-XXXX 3. Si ARCA configurado: - reserva cbteNro (→ PENDING_CAE) - pide CAE a ARCA - OK → ISSUED con CAE - falla → PENDING_CAE + fiscalError (botón reintentar) 4. Si NO hay ARCA → ISSUED interna SIN CAE (no fiscal)

9. Flujo de impresión

1. Click "Imprimir" (listado o detalle) 2. Se monta <PrintInvoice {datos} /> (hidden print:block) 3. window.print() → diálogo del navegador 4. CSS @media print oculta el resto y muestra solo .print-area 5. Navegador imprime/exporta a PDF el comprobante (con QR + CAE si está emitida; si no → "no válido como factura ARCA")

10. Gotchas que conviene conocer

  • Carrera de correlativo: getLastInvoiceNumber corre fuera de transacción. Si dos emiten a la vez, pueden obtener el mismo cbteNro y ARCA responde "ya registrado" → el código consulta el CAE... que es el de la otra factura (edge case real de concurrencia).
  • Condición IVA del receptor con DNI hardcodeada a 5 (Consumidor Final) aunque por norma podría ser RI.
  • El issue devuelve 200 con fiscalError adjunto cuando la emisión fiscal falla (en vez de 500) — el front lo interpreta para mostrar toast distinto.
  • El padrón en homologación solo acepta los CUITs de prueba de AFIP; los reales dan "No existe persona" hasta que ARCA habilite producción (ticket 46924530).

11. Bug conocido: LoginCms WSAA

El LoginCmsReturn de WSAA no contiene base64 del TA — contiene el XML del TA en texto plano escapado dentro del SOAP. El parser lo des-escapaba a string plano. La estructura interna del TicketAcceso es loginTicketResponse con <header> (source/destination/uniqueId/generationTime/expirationTime) y <credentials> (token/sign).
